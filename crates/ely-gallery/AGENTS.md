# AGENTS.md: ely-gallery

The gallery, its capture harness, scripts, stories and web build.

## Stack

- Windows capture: `windows-sys` 0.59 (MIT OR Apache-2.0, the gallery's, Windows only) has the window draw itself through `PrintWindow`, which holds what DirectX presents; `raw-window-handle` 0.6 finds the window.
- Web: on wasm32, `web-time` 1.1 (MIT OR Apache-2.0) gives the `Instant` gpui's executor returns, std's own natively; jiff takes `js`, similar `wasm32_web_time`. The gallery's web entry takes `gpui_web`, `wasm-bindgen`, `js-sys` and `web-sys` as wasm-only dependencies, and a Hebrew cut of Noto Sans Hebrew 2.003 (OFL, `crates/ely-gallery/fonts`): gpui_web asks the browser for emoji and CJK alone. The `wasm-bindgen` CLI at Cargo.lock's version and binaryen's `wasm-opt` finish the bundle.

## Commands

- `cargo run -p ely-gallery` opens the gallery. `-- --page <slug>` starts on a page; `--story <title or slug>` with it draws that section alone, and `--capture` then shoots it without the page's script.
- `cargo run -p ely-gallery -- --capture <dir>` writes PNGs of every page, light and dark, top to bottom, then each page's scripted states, including windows the demos open. macOS plays the scripts; Windows and Linux shoot the pages alone, as a script's input is posted through AppKit. Linux shoots an X11 window (unset `WAYLAND_DISPLAY`; under Xvfb with Mesa's lavapipe where there is no GPU). A capture holds every drawn time at one moment (`capture::AT`), so two captures of one build match pixel for pixel. A page is shot once its height holds, and each view once it holds still for 1.1 s, shots 250 ms apart (`capture::steady`), so neither a picture still decoding nor a counter between ticks is caught; a view still moving after 4 s, a ticker, a GIF, a frame meter, is logged and the pixels that moved in its last 1.1 s saved beside it as `NAME.moving.png`, which `scripts/pixels.py` passes over; what moved once and settled stays compared. `--window WxH` opens the window at that size (a capture resizes a window the system gave another, as macOS gives 600 or 601 tall, and fails if it cannot) and shoots the pages alone, since scripts aim at the usual 1280 by 820; `pixels.sh` asks 1000x600, which a hosted runner's 1024x768 screen never trims, so every platform compares pages alone. `--still` makes `ui::live` start no demo, so a terminal's shell or a stepping number never shows mid-run; `pixels.sh` passes it, `scripts/shots.py` does not. A script that drives a live demo opens with `Step::Live`, which ends it where the demo does not run.
- `cargo run -p ely-gallery -- --narrow 280 --capture <dir>` lays each page, header and body, at that width in a padded card and shoots it without its script, whose aims are measured at full width. Demos that set their own width run past the card.
- `RUSTC_BOOTSTRAP=1 cargo check --lib --target wasm32-unknown-unknown` checks the web build; gpui_web's `wasm_thread` needs the bootstrap, as Zed's web examples do.
- `ELY_GALLERY_ASSETS=<address of out/assets/> scripts/web.sh <out>` builds the gallery for the browser, profile `web`, and fails past Cloudflare's 25 MiB. It opens at `?page=<slug>&story=<title or slug>&theme=light|dark`; the host page calls `gallery.setTheme(mode)` or posts `{ ely: "theme", theme }`, before the wasm runs or after, and the page posts `{ ely: "ready" }` to its parent once it runs.
- `cargo run -p ely-gallery -- --audit <report.tsv>` (Windows) tabs through every page under a UI Automation client and writes each stop's role, name and place; it exits 1 on a stop a screen reader cannot name. CI's Windows leg runs it. It takes the window's focus for about nine minutes.

## Layout

- `crates/ely-gallery`: the gallery's sources in `src/` (binary `gallery`), its pictures, fonts, `index.html` and `stories.json`, and the docs examples in `examples/docs`.
- `crates/ely-gallery/src/pages/<chapter>.rs`: one page per chapter, in PRD order.

## Rules

- A capture parks the pointer on `shell::REST`, the sidebar's title or, under `--story`, the 32px band above the story's scroll box, on every OS, before each page and at a script's `Rest`: a fixed point lands on whatever a window size lays there, a hovered row at 1000x600. macOS posts the move through AppKit; elsewhere it goes through `Window::dispatch_event`, since gpui keeps where the OS last saw the cursor, and on Windows the system cursor moves there too (`capture::point_cursor`), since Windows sends a window a move at the real cursor when what lies under it changes: a capture moves your pointer.
- The gallery scripts mouse input by posting `NSEvent`s to its own queue, so a press takes AppKit's path and reaches a native view over the window (`misc::WebView`). `Window::dispatch_event` reaches only gpui's listeners. gpui's normal window takes mouse moves from a tracking area, which only a real cursor feeds, so the harness sets the window's `acceptsMouseMovedEvents` for posted moves.
- gpui starts a drag on the first move past its threshold, and only the moves after it reach `on_drag_move`. gpui 0.2.2's mac window replayed a held drag every 16 ms; gpui_macos replays only while `pressedMouseButtons` shows a real button, which posted events never set. So `Step::DragTo` posts each move twice, as the replay did: the second post of the first step reaches `on_drag_move`, where a component that anchors on its first drag move sets its anchor (Scrollbar, Knob, Split).
- gpui 0.3.10's atlases pack pictures with `padding: 0` and sample them linearly, so a scaled picture's edge row takes its atlas neighbour's color, and pictures decoding in another order change that neighbour: a lone changed edge row in a `pixels` report (macOS `media-*-4`, `VideoPlayer`'s top row) is this, open upstream.
- Every shot of a gpui window, a page's or a script's, waits three of its frames through `on_next_frame`: gpui presents without waiting on the GPU, and a heavy page's draw outlasts a fixed pause, so a shot could show the frame before the last step. A page's pauses stay, for work off the main thread such as pictures decoding. A covered window draws no frames, so its capture fails after 5 s instead of shooting a stale frame.
- The capture harness turns on reduced motion, so shots are still: repeating motion rests on one frame, and a shimmer shows no band. gpui's mac window stops its display link while occluded, so a capture advances a moving picture only on the draws the harness forces.
- Each capture pass starts its page fresh (`Gallery::fresh`): page state lives under the pass, so the dark pass runs its script from the same start as the light one.
- The capture harness finds gpui windows by handle through `raw-window-handle`. AppKit popups, which gpui does not own, come from the window list by process and level.
- Posted events cannot move a macOS window, so window drags are not scripted. `drag_region` follows Zed's title bar.
- The macOS share picker draws its content in another process; a capture shows only its frame.
- NSColorSampler runs in another process too. The harness cannot pick or cancel with it; `read_srgb` is tested on a constructed `NSColor` instead.
- The harness types with `dispatch_keystroke` through `AnyWindowHandle`, which leaves the root view free to redraw.
- The macOS open panel runs out of process too. Escape does not reach it; the harness sends it `cancel:`.
- Quartz scroll events carry no window. The harness hands them to the window itself, placed in window points (`Step::Swipe`).
- Script clicks aim at a probe's corner, so a scripted target must fit in the window; a tall probe puts its top off screen, and an aim outside the window fails the script. The log names each probe's bounds as the script aims, and a probe around content with no width of its own measures smaller than what it draws, so a scripted demo sets its width.
- A shell in the gallery starts without startup files and with a fixed prompt, so captures show no user or host.
- What a browser cannot run draws natively alone: `ui::native_only` leaves a window's opener out on the web, and the web's menu bar keeps View alone. The site shows native captures instead, light and dark: a story whose demo needs the desktop (files, the terminal's shell, the tray, the Dock, window moves) as its capture, and a live story that opens windows with those windows below. `python3 scripts/shots.py` takes them with the native gallery, window in front, into `frontend/public/shots` and `frontend/src/shots.json`.
- A story is a gallery section: its title is a literal, one per page. Under `ui::Story` the one asked for draws without its title; the rest drop their demos (`ui::Section`), so nothing of theirs lays out, loads or moves. Their builders still run, so a demo that starts work on its own, a clock, a load or a shell, starts it through `ui::live`, which a story grants its own section alone and fails on a title no section has. A story the page lacks fails in the page.
- Embedded in a page, the web gallery keeps gpui_web's hidden text field from taking focus, and hands focus back to the host, until a press or a key reaches it (`crates/ely-gallery/index.html`); gpui_web focuses that field whenever its window is active. It retries a failed start twice, since frames that fetch the wasm at once can fail one, then posts `{ ely: "failed", error }`. The host shows its own state until `{ ely: "ready" }` or that failure, sends the mode on ready and on every turn, and puts a skip link before the frame, since Tab inside gpui cycles within it.
- The gallery's pictures go through `asset!` and `ui::picture` or `ui::resource`: a file natively, on the web an address under `ELY_GALLERY_ASSETS`, since gpui reads no files there.
- Embedded, the web gallery ignores its own `focus()` calls until a press or key reaches it, so a frame that starts never takes the host page's focus; the site keeps a focused frame mounted (`frontend/src/pages/Home.tsx`'s `Near`).
